**Known issues**
- GrandTechHub orders have never been observed reaching a successful terminal state; known orders remained `PENDING`/`PROCESSING`.

- **Fixed: instant-data wallet leak on order-insert failure (`create-public-data-payment`).** The function charged the agent wallet, then inserted `public_data_orders`; if that insert threw, `orderId` stayed `null` and the catch block (`if (orderId && reference)`) skipped the refund, so the agent was debited with no order and no refund. It now records `chargedAgentId`/`chargedAmount` immediately after `chargeWallet` and, in the catch, refunds whenever the wallet was debited (looked up by `payment_reference`; falls back to the in-memory amount when the row was never created). Also wrapped `buyDataPackage` in try/catch so a provider exception still calls `complete_agent_data_order` — previously the company's `reserve_agent_data_order` debit could be left stuck in `processing`. `deno` is not installed in this environment, so this was reviewed by hand, not type-checked. **Deployed 2026-10-10.**
- **Fixed: utility-bill checkout was charging 1.5% on top of the bill (`create-utility-bill-payment`).** It computed `grossAmount = netAmount / (1 - 0.015)` and made the wallet pay that gross while the customer saw only the net amount — a silent 1.5% overcharge on every utility payment. Now `feeAmount = 0.00`, `chargeWallet` uses the exact `netAmount`, and the response/ledger match. Frontend: `utilityBills.js` removed `calculateGross`/`FEE_PERCENT` entirely — `updateSummary()` and the review modal show fee `0.00` and total = net — and `utilityBills.html` defaults are `0.00`/`50.00`. `airtime.html` default total corrected too (`10.00`). **Deployed 2026-10-10.** All other purchase paths (data bundles, instant data, AFA, results checker, airtime) already charge exact server prices with zero gateway fee; the fee lives only in wallet funding (`create-agent-wallet-payment`, `paystack-webhook`).
- **Fixed: stale wallet balance on the banner/footer.** The banner read the `profiles.wallet_balance` mirror (recreated by the Hubtel migration, so it could lag or be wrong) or nothing at all on load. Now every bundle purchase page refreshes the authoritative `wallets.balance` on load: `airtime.js` imports and calls `refreshWalletBalance()`, `data.js` `loadBalance()` reads `wallets.balance` first (profiles mirror is only a fallback), and `walletBalance.js` `applyWalletBalance()` also fills `#walletBalance`, `#popupBalanceVal`, `#walletHeaderDisplay`. `instantData.js`, `instantDataModal.js`, `resultsChecker.js`, `utilityBills.js` and `nonAgentBuyers.js` already refreshed on load.
- **Migration `20261010000000` applied: `profiles` identity columns restored.** Live `profiles` had been rebuilt to the Hubtel shape (`id, email, wallet_balance`) — `full_name`/`phone`/`agent_code` were missing (probes returned HTTP 400) — so `ensureAgentProfile`'s upsert failed and a fresh agent code was generated on every sign-in. The column now exists (verified via PostgREST), the existing `Agents can update their own agent row` RLS policy already permits the browser to write it, and the trigger now copies it to `profiles` on every agent write. Three migration errors were fixed on the way: `to_regcolumn` does not exist on this remote (switched to `information_schema` lookups), the trigger's `UPDATE OF phone` clause was invalid where `agents.phone` was absent (now `after insert or update`), and phone was missing entirely from the live `agents` shape (added by `20261010010000`).
